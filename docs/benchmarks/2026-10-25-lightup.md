# Light Up baseline: 25 October 2026 (Linux)

Command per input:

```sh
uv run python -m light_up_problem.benchmark --size {7,10,14,25} \
  --difficulty {easy,normal,hard} --algorithms dfs astar \
  --repeats 3 --timeout 30 --csv /tmp/lightup-bench/<size>-<difficulty>.csv
```

The [raw CSV](2026-10-25-lightup.csv) holds all 72 runs (12 inputs × 2
algorithms × 3 repeats) on the sample seeds (`get_sample_puzzle`). Both
algorithms get identical puzzles and limits: 30-second timeout, 500,000-node

"Bulbs" is the returned `solution_cost` (median run). On the five inputs both
solvers finished, A* always returned the minimum-bulb count; DFS matched it
twice (7-easy 7, 7-hard 6) and used more bulbs on the other three (8 vs 7,
11 vs 10, 12 vs 9).

Environment: Python 3.13.14, pygame-ce 2.5.8, Linux 6.8.0-138-generic x86_64.
Time is the solver's own `perf_counter` measurement; peak memory is the
`tracemalloc` peak of Python allocations during the solve, not process RSS.
TIMEOUT rows record the 30-second budget, not a completion time; an exhausted
search would instead report UNSOLVABLE, which never occurred here.

Reading: DFS with the shared pruning solves all twelve inputs, expanding as few
as 7–35 states on most boards (the first-unlit branching plus feasibility
pruning follows an almost straight placement sequence). A* proves minimum-bulb
solutions but pays for the frontier, duplicate table and per-expansion bound
computation: it is 9–250× slower where it finishes and times out from
10×10-hard upward. At 25×25 it expands only 15–37 states in 30 seconds because
every expansion recomputes bounds over ~500-cell masks.

## Extended-budget A* reruns (600 s)

The 30-second timeout is an experimental design choice of this project; the
assignment brief does not mandate any limit. To check that the seven TIMEOUT
rows above are not an artifact of a too-small budget, A* alone was rerun once
per input with a 600-second timeout (same node/memory limits). All seven still
timed out. Raw rows: [2026-10-25-lightup-ext.csv](2026-10-25-lightup-ext.csv).

| Input | Status | Time (s) | Peak alloc (KiB) | Expanded |
|---|---|---:|---:|---:|
| akari-10-hard-100291 | TIMEOUT | 600.0 | 72,003 | 151,546 |
| akari-14-easy-140097 | TIMEOUT | 600.0 | 16,405 | 19,638 |
| akari-14-normal-140194 | TIMEOUT | 600.0 | 16,120 | 8,634 |
| akari-14-hard-140291 | TIMEOUT | 600.0 | 31,244 | 9,477 |
| akari-25-easy-250097 | TIMEOUT | 600.0 | 1,868 | 523 |
| akari-25-normal-250194 | TIMEOUT | 601.8 | 2,649 | 425 |
| akari-25-hard-250291 | TIMEOUT | 600.2 | 9,121 | 1,359 |

Even with a 20× budget A* does not finish: on 10-hard it expanded 151,546
states and retained ~70 MiB of traced allocations within 600 seconds while the
frontier kept growing. On the 25×25 boards the per-expansion cost (~1–2 s over
~500-bit masks) means only 425–1,359 states are reached in 10 minutes — far
below what an optimal-proof search over such boards requires. TIMEOUT here is
therefore a genuine resource-exhaustion outcome, not a near-miss.
